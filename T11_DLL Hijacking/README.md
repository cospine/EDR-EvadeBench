# T11: DLL Hijacking

**DET classification:** Detection → Memory Concealment

This technique, specifically implemented using **DLL Proxying**, abuses the way Windows loads Dynamic Link Libraries (DLLs) by leveraging the DLL Search Order Hijacking vulnerability. When a vulnerable application attempts to load a DLL, it searches in a specific, predictable order.

The successful attack chain involves:

1.  **Placement:** Placing a malicious Proxy DLL (e.g., named `libcurl.dll`) into an accessible folder that is searched *before* the legitimate, system-provided DLL (e.g., `C:\Windows\System32\libcurl.dll`).
2.  **Hijacking:** The victim executable loads the malicious Proxy DLL first.
3.  **Execution and Proxying:** The malicious code executes its embedded payload (often in `DllMain`). Crucially, the proxy DLL then loads the *original* system DLL and exports all original functions, seamlessly forwarding API calls.

This sophisticated method ensures the malicious payload executes within the trusted context of the victim application without breaking the application's functionality, making detection difficult.

## 📊 Evaluation Results

> Aggregated over **36 test-case outcomes**: 3 payload families (Cobalt Strike, Havoc, AdaptixC2) × 6 products × 2 Windows environments (Windows 11 Enterprise, Windows Server 2025), each scored on the five-tiered prevention-stage model (L1–L5).

**Overall effectiveness.** The technique reached **L5 (Operational Success) in 36.1%** of its 36 outcomes — the highest L5 rate among the Memory Concealment techniques.

**Interpretation.** Executing the payload inside a trusted application via search-order hijacking and proxying was the most successful Memory Concealment implementation: Microsoft Defender Antivirus reached L5 in 5 of 6 outcomes, and Kaspersky and Huorong each in 4 of 6. The technique is strongly payload-dependent — 8.3% with Cobalt Strike versus 50.0% with both Havoc and AdaptixC2 — which the paper cites as a concrete example of insufficient generalization across payload implementations.

## ⚙️ Usage (Defensive Research)

The implementation requires tooling (like AheadLibEx) to generate the necessary function forwarding code and embedding the EDR-EvadeBench payload into the Proxy DLL's `DllMain` routine.

### Prerequisites

* The source code for the Proxy DLL (including the forwarding mechanism).
* Your own (AES-encrypted) EDR-EvadeBench shellcode payload.
* A target executable that is vulnerable to loading a specific DLL from its local directory (e.g., `TargetApp.exe`).

### Detailed Execution Steps

1.  **Generate Proxy DLL:**
    * Use a tool (e.g., AheadLibEx) to generate the Proxy DLL project for the target system DLL (e.g., `libcurl.dll`).
    * Integrate the EDR-EvadeBench payload loader (shellcode decryption, VirtualAlloc, CreateThread) into the Proxy DLL's `DllMain` function under the `DLL_PROCESS_ATTACH` section.
    * Compile the project to produce the final malicious Proxy DLL (e.g., `libcurl.dll`).

2.  **Stage the Attack:**
    * Place the malicious Proxy DLL (`libcurl.dll`) into the same directory as the vulnerable `TargetApp.exe`.

3.  **Execute the Target Application:**
    * Run the target application:
        ```bash
        TargetApp.exe
        ```
    * The application will load the malicious Proxy DLL first, executing the payload in `DllMain`. The subsequent API calls will be seamlessly forwarded to the real system DLL.

4.  **Validation:**
    * Verify that the payload executes and the host application continues to run normally.
    * Inspect the host process using Process Explorer to confirm that the malicious DLL was loaded and the suspicious thread activity originated from within the trusted process's address space.

> **Warning:** Due to the complexity of path resolution, proper DLL Search Order Hijacking requires careful selection of the vulnerable application and its dependencies. Execute this PoC **only** in isolated VM environments.

## 🧪 Validation Criteria (paper, Table 7)

- **Required privilege:** Standard User.
- **Evasion-logic criterion:** the malicious DLL is loaded by a legitimate
  application via search-order hijacking, its entry point executes, and the
  payload runs inside a trusted process context.
- **Payload-functionality check:** C2 beacon observed within 60 seconds, and
  the beacon answers test commands.

## 🛒 What You Must Supply

This folder contains the **proxy** half of the technique. To exercise it you
also need:

1. a **target application** that loads a specific DLL from its own directory
   before the system copy — the paper's evaluation used a vulnerable
   third-party application, which is not redistributed here;
2. the **genuine DLL** the proxy forwards to (this build proxies
   `libcurl.dll`), so the forwarded calls can be resolved.

Place the built proxy in the target application's directory, next to the
executable.

## 🧹 Cleanup / Recovery

Delete the proxy DLL from the target application's directory. Nothing is
persisted; the hijack exists only as file placement.

## ⚠️ Known Limitations

- Search-order hijacking depends on the target application's load path and on
  whether the DLL is already loaded (or present in `System32`) before the
  application starts.
- Proxying every export is fragile across versions: if the genuine DLL's
  export set changes, the forwarded exports must be regenerated.
- The technique is strongly payload-dependent in the paper's results, which
  is why the payload you supply materially changes the outcome.
